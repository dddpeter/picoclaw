四、逐项诊断与最小重构方案

P0#1 ExecuteTools：848 行单方法，认知复杂度 410（全库第一）
位置
pkg/agent/pipeline_execute.go:121（文件共 965 行，此函数占 848 行）
证据
认知复杂度 410 / 圈复杂度 101；内含两个大型 switch decision.normalizedAction()（审批决策流 + 工具分发流前后串联）；11 个 case 分支
症状
一个方法同时负责：工具审批流、工具分发、skill 名推断（inferSkillNamesFromToolCall）、媒体引用解析、错误摘要、流式面板反馈、工具执行记录。六种职责纠缠，"深模块"应有的窄接口被内部细节淹没。
影响范围
每轮对话必经的热路径。但调用点唯一：turn_coord.go:254（runTurn），重构不外溢出包。
最小重构
纯内部拆分，不改签名、不改行为：① 把两个 switch 各自提取为 handleApprovalDecision() 与 dispatchTool()；② 每个 case 分支体提取为 execToolXxx 私有方法；③ 分发处改查表 map[string]toolHandler。目标：单函数 ≤ 120 行，每片认知复杂度 ≤ 40。先跑现有 agent 测试套件建立基线再动手。
理由
唯一调用点 + 包内私有 = 零 API 破坏；这是全库理解成本最高的函数，收益/风险比最优。
预估
1.5~2 天（含测试回归，agent 套件约 70 秒）。
P0#2 CallLLM：704 行 + 循环内 10 处线性扫描（潜在 O(n²)）
位置
pkg/agent/pipeline_llm.go:28
证据
认知复杂度 175；linear_scan_in_loop = 10（find/contains/indexOf 式扫描出现在循环内，消息列表按名匹配等模式）；流式降级（streamingDegraded）、fallback 候选、hooks 改写、重试判定混在同一方法体
症状
LLM 调用的编排逻辑（流式/非流式/降级/重试/fallback/hooks）全部内联；704 行里任何一处改动都要通读全文。
影响范围
每轮对话必经。调用点唯一：turn_coord.go:220。
最小重构
① 提取 callStreaming() / callNonStreaming() 两分支为独立方法；② 重试环提取为 retryLoop()；③ 把循环内的线性扫描改为循环外构建一次 map 索引（先 benchmark 证实热点，fmt 见下）；④ 保持 streamRoundTripper 语义不变。
理由
与 #1 同属流水线双巨头，但此处涉及流式语义（fork 红线区），所以方案刻意保守：只做方法提取与索引化，不动传输层。
风险
红线 fork 关键行为：ChatStream 独立流式 Transport、响应头超时 90s、`streamRoundTripper`——重构禁止触碰 openai_compat 传输层；现有流式响应头超时测试必须保持绿。
预估
1.5 天（先补一个含降级路径的回归测试再动手）。
P0#3 AddModelSheet vs EditModelSheet：647/846 行相同（~78% 重复）
位置
web/frontend/src/components/models/add-model-sheet.tsx（846 行）与 edit-model-sheet.tsx（822 行）
证据
排序后取交集 647 行完全一致（含整段 import 块、字段渲染、FetchModelsDialog 集成、保存逻辑）；两文件 1668 行合计
症状
典型复制粘贴演化：任一表单字段/校验规则改动必须双处同步，已经/即将漂移。这是全库最大的一块机械重复。
影响范围
仅这两个文件 + 新建共享模块；模型管理页（ModelsPage）不感知内部结构。
最小重构
提取 ModelFormSheet 共享组件 + useModelFormState() hook（字段、校验、FetchModels 集成全部下沉），两个 Sheet 各自只保留：标题文案、初始值填充、提交端点（POST vs PUT）。预计净删 ~550~650 行。
理由
重复度极高且边界清晰（add=空表单+POST，edit=预填+PUT），提取风险低、收益立竿见影；建议作为 P0 里第一个动手项（前端改动不碰 Go 热路径）。
预估
1 天（含手工验证两条表单路径）。
P1#4 turnState（~70 字段）+ turnExecution（~30 字段）上帝结构体
位置
pkg/agent/turn_state.go:119/204
证据
turnState 约 70 个字段（含锁、心跳原子量、流式发布器、skill 追踪、媒体、followUps…）；pkg/agent 内 28 个文件引用 turnState——这是包内隐藏耦合的最大来源：任何文件都能读写任何字段，字段所有权无人知晓
症状
典型的"浅模块 + 共享可变状态"：Pipeline 各阶段通过同一坨状态传递，数据流不可见；配合 66 文件的巨型包，新人无法建立心智模型。
影响范围
波及 pkg/agent 全包（28 文件）——爆炸半径大，严禁一步到位重构。
最小重构
分三步走且只走第一步：① 文档化字段所有权——在结构体上按"阶段写者"重排并注释（SetupTurn 写哪些、CallLLM 写哪些、ExecuteTools 写哪些）；② 把 turnExecution 中每迭代重建的字段抽成 iterationState 子结构（创建点唯一：newTurnExecution）；③ 其余留待 #1/#2 拆分时顺势收口。禁止改 turnState 的锁语义。
理由
结构体是全包枢纽，动它的成本远高于先给 #1/#2 拆函数；字段分组是零行为变更的纯机械动作，却能让后续所有重构有地图可依。
风险
红线 turn 全程持有 agent 模型状态读锁（runTurn）——任何命令路径禁止无超时拿写锁；turnState 的 mu 语义不得改变。
预估
第①步 0.5 天；第②步 1 天。

P1#7 web/backend 与配置文件的隐式耦合
位置
web/backend/（main.go 401 行、api 包 26 文件 12,687 行）
证据
边界扫描：backend→config 1080 次调用（全库最重边界）；backend 直接读写 config.json，与 gateway 的 mtime 轮询热重载构成跨进程文件级时序耦合；api.Error fan-in 387
症状
两个进程（backend、gateway）通过同一配置文件通信，耦合不可见：backend 写文件 → gateway 下一分钟轮询到 mtime 变化才生效。AGENTS.md 已记载 Windows rename 竞争问题——这是结构性根源。
最小重构
收口写路径：backend 内所有配置写入集中到一个 configStore（原子写 + 变更通知封装），禁止 handler 各自读写文件。读取路径暂维持现状（1080 处全改不现实）。main.go 按 CLI/服务/tray 三段拆为 runWebServer() 等。
理由
写路径是竞争与不一致的源头，收口一处即可消除整类问题；读路径 fan-in 太大，留待长期演进（如 gateway 暴露配置 API）。
预估
写路径收口 1 天；main.go 拆分 0.5 天。

P2#9 命名混乱：三个"会话之家"、三代上下文管理器、两套总线
证据
① 会话概念散落三处：pkg/memory（JSONL 底层存储，978 行）→ pkg/session（包装层 metaAwareStore）→ pkg/agent/sessions/（运行时数据目录，源码树里的非代码目录）。三者名字几乎不可区分，但分层本身是合理的（已验证 memory 被 session/agent/web 三方引用，非死代码）。
② 上下文管理器三代同包共存：context.go / context_legacy.go / context_seahorse.go——legacy 版仍在 turn_coord.go:370/377/385 作为 seahorse 关闭时的回退路径，是活代码。
③ pkg/bus（频道消息路由，MessageBus）与 pkg/events（运行时事件总线，EventBus）职责不同但名字都不体现差别。
最小重构
不改任何包名（破坏面远大于收益）：在 docs/design/fork-overview.zh.md 补一张"会话/上下文/总线"概念地图；给四个包的 doc 注释各加 3 行角色说明；pkg/agent/sessions 数据目录确认加入 .gitignore（当前未入库，保持）。
理由
命名问题的最小修复是"地图"而非"搬家"——重命名包会破坏 100+ import 点与上游同步。
预估
0.5 天（纯文档）。

六、方法论与局限
